## nucula-c3: root-caused, recovered, hardened

### What happened (from the console-c3 journal + flash coredump)

1. **Fw panic** sometime in the 04:40–12:48 window on 2026-10-26, with a
   random-ID tag coupled to the PN7160 antenna (card traffic visible
   22:36→23:4x, `pn7160_nci::esp_transport: read_frame` spray class).
   Coredump (28,068 bytes) written to the coredump partition.
   Decoded against a rebuilt c562a1d ELF: panic context is INSIDE an
   interrupt (`_interrupt_handler`, vectors.S), the ISR was touching
   ASSIST_DEBUG registers (`0x600ce000` = DR_REG_ASSIST_DEBUG_BASE —
   the C3's stack-bound monitor), systimer conversion frames on the
   stack, and one task was in `esp_system_reset_modules_on_exit`
   (a reboot was already in flight). Signature reads as an interrupt-
   watchdog / stack-monitor class panic during PN7160 churn.
2. **Deterministic hang at `app_main()`** on every subsequent boot of
   that build (60+ boots, incl. my own hard resets): IDF boot logs reach
   `main_task: Calling app_main()` — the exact point where the fw claims
   the `UsbSerialDriver` (#186) — then total console silence. USB stays
   up (esptool talks fine). Not image corruption (bootloader verified the
   image, ran to app_main every time); NVS is unchanged and boots fine
   under the new fw, so it was an old-build fw bug triggered by state
   left from the crash. Wedged build: `libespidf` Oct 23 2026 18:28:17,
   app elf_sha256 `58d45360 92c1 92a6 …` (built from an esp-idf-sys cache
   of that evening — the c562a1d re-flash claimed in the known-good stamp
   did not match this sha, so the board was NOT running the documented
   image when it wedged).
3. **The "console garbage" was the wedged fw + a host-driven reset
   storm.** pyserial reads on the stalled CDC device raise
   "device reports readiness to read but returned no data" →
   `bolty-console` exited (`os._exit(3)`) → systemd restarted it
   (RestartSec=10) → **every reopen pulses DTR/RTS through pyserial's two
   sequential TIOCMBIC ioctls (cdc_acm rejects atomic TIOCMSET with
   EINVAL), and on the ESP32-C3 USB-Serial/JTAG console the
   DTR-low/RTS-high intermediate state is a `USB_UART_CHIP_RESET`
   (rst:0x15)**. Restart counter hit 38; the board was reset every ~6.3 s
   for 10+ minutes (23:48→23:58 window, also 12:48). The "binary garbage"
   was a structured repeating dump (`03 06 65 …` with 0x61..0x69 walking
   bytes) the wedged fw emitted ~6 s after each boot, right before each
   host reset.

## m5stick: RESOLVED REMOTELY 2026-10-27 — reader was LATCHED, not dead
## (fw `grove on|off` AXP EXTEN cycle = the permanent fix; no hands needed)

Console daemon healthy throughout. Death timeline from the console journal
(time-of-day stamps; ordering is chronological):

- Oct 25 04:51:46 — boot #5 (POWERON): `hw: i2c_scan=0x28` — MFRC522
  ALIVE. That uptime ran ~24 h and included an unattended soak of ~22
  burn cycles / 91 picc reads / 5 wipes on card `043365FA967380`
  (the #444 follow-up workload class; finished fine).
- Oct 26 04:55:01 — board IDLE (heartbeats only, no card op in flight):
  `rst:0x1 (POWERON_RESET)` — a stick-local brownout (ZERO kernel USB
  events that day: the FT232 stayed up, so VBUS never dropped). Next
  boot #6: `hw: i2c_scan=none`, `nfc=missing`.
- Oct 27 04:49 — boot #7 (POWERON), again with zero kernel USB events:
  the SAME stick-local brownout class, ~4:5x AM twice in a row. Reader
  still invisible. (Recurring-brownout pattern flagged for watching.)

Root cause of the reader outage: **the brownout left the MFRC522
latched, and no ESP32 reset can clear it** — the AXP192 is a separate
chip that holds the Grove 5 V rail (EXTEN boost) across ESP32 POWERON
resets, so the reader's supply never dropped again after the glitch.

Resolution (2026-10-27, zero hands): flashed fw with the new `grove
on|off` console command (AXP192 EXTEN bit — remote power lever over the
display's I2C1, which is independent of the wedged I2C0). Test sequence:
`grove off` (6 s) → `grove on` → `i2cscan: found 0x28` — first time on
the bus since Oct 26. One reboot to re-run NFC init against the healthy
reader → boot banner `hw: nfc=ok i2c_scan=0x28`, heartbeats `nfc=ok`,
`check` runs the field (fail = "card not present" — no card is lying on
the m5 antenna right now, which is a placement fact, not a defect).
Stick now on main + grove (elf `91db62bb…`).

FOR THE FUTURE: this failure class (brownout-latched reader) is now
self-service — `grove off` → `grove on` → reboot. The AGENTS "needs a
hands visit" verdict is superseded.

## Shared /run/bolty pitfall (found + fixed while flashing)

`bolty-console.service` (m5stick) declared `RuntimeDirectory=bolty`;
stopping it for the flash made systemd DELETE `/run/bolty` — including
the c3 daemon's live socket. The c3 daemon stayed "running" while
listening on an unlinked inode (all client connects fail). Fix: no unit
owns the directory (both daemons already `os.makedirs` it themselves);
deployed units updated 2026-10-27.
