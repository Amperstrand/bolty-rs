## Result

**The skeleton boots and logs on the F469.** All three expected defmt
lines are emitted, then the core sits quietly in the WFI loop at
`apps/bolty-stm32/src/main.rs:122` (confirmed with a gdb hardware
breakpoint; DWARF-accurate). No panic, no hardfault on the success path.

RTT transcript (decoded offline from an SRAM dump — see "probe-rs
finding" below):

```
0.000000s  INFO  bolty-stm32: initializing...
0.000000s  INFO  bolty-stm32: heap initialized (N bytes)
0.000000s  INFO  bolty-stm32: skeleton ready — implement hardware init
```

Flash/verify path that works on this bench (mirrors ccid-firmware-rs):

```bash
arm-none-eabi-objcopy -O binary target/thumbv7em-none-eabihf/release/bolty-stm32 \
  target/thumbv7em-none-eabihf/release/bolty-stm32.bin
st-flash --connect-under-reset --serial 066FFF515786534867184152 \
  write target/thumbv7em-none-eabihf/release/bolty-stm32.bin 0x08000000
st-flash --connect-under-reset --serial 066FFF515786534867184152 reset
```

## Four build-config defects fixed (same PR)

All four were invisible to host builds and to a plain "it compiles" check;
each one alone silently kills RTT bring-up. All four match what
ccid-firmware-rs already does on the same chip:

1. **`strip = true` removed from `[profile.release]`** — the ELF symtab
   carries `_SEGGER_RTT`; without it probe-rs cannot locate the RTT
   control block. (Flash image is unaffected — symtab is host-side.)
2. **`-Tdefmt.x` added to the target rustflags** — anchors/merges the
   `.defmt.*` interned-string sections and their EXTERN retention.
3. **`[env] `DEFMT_LOG = "info"`** in `.cargo/config.toml` — defmt-macros
   filters log statements at COMPILE time, env_logger-style; with
   `DEFMT_LOG` unset the default level is Error and **`info!()` compiles
   to nothing** (verified at disassembly level: pre-fix `main` contained
   only heap-init + `wfi`).
4. **`debug = 2` in `[profile.release]`** — defmt 0.3.100 stores interned
   format strings in DWARF metadata; without debug info probe-rs cannot
   decode frames at all.

## probe-rs finding (open)

`probe-rs run`/`attach` (0.32.0) never printed RTT for this skeleton on
this board, even with the fixed ELF: traces show 118–190 scan retries at
the exact symbol address (`0x20000008`) all failing with "control block
not found", while SRAM read via st-flash (which halts the core) contains
a perfect control block with the three frames. `run` also performs
`reset_and_halt` + "Clearing RTT control block" before polling.

Working hypothesis: memory reads while the core is **WFI-sleeping** do
not work over this ST-LINK/board (ccid-firmware never sleeps — its RTT
always worked; every successful read in this session happened with the
core halted). Future hardware-init should keep this in mind (either a
wakeup source with a poll loop, or plan on halt-then-read tooling).

Evidence transcript capture therefore went through: st-flash SRAM dump →
offline rzCOBS decode against the ELF tag table (byte-exact encoder
simulation for frames 1 and 3; frame 2 including the `{}` argument
plaintext). Decoder scripts are in the evidence pack.

Also observed: `RCC_CSR = 0x1e000000` (IWDGRST|SFTRST|PORRST|PINRST).
ccid-firmware-rs uses only a DWT software watchdog, so the IWDG flag most
likely predates this session; no live-watchdog resets were proven either
way during this session. If a future lane suspects a stale hardware
watchdog, one USB replug (POR) settles it.

## What the skeleton's TODOs need (bring-up notes for the next lane)

From `apps/bolty-stm32/src/main.rs` — none of this was attempted in this
session (skeleton scope only):

1. RCC clock init (the skeleton runs on reset defaults).
2. I2C peripheral + pins for the MFRC522 (`I2C1`, ~100 kHz, address
   `mfrc522_pcd::DEFAULT_I2C_ADDRESS` — on the ESP32 rig the MFRC522
   answers at 0x28 over I2C).
3. UART console pins.
4. `Mfrc522Transceiver::from_i2c` → `Mfrc522Transport::activate`, then
   the bolty-core/bolty-ntag stack runs unchanged from the ESP32 side.
5. Watchdog policy: decide whether the F469 build should enable/feed the
   IWDG (ccid-firmware does not; if anything ever enables it, remember it
   survives system resets and only a POR clears it).
6. probe-rs RTT: resolve or work around the WFI-scan issue above before
   relying on `probe-rs run` transcripts on this bench.
